Zmiany przygotowano i sprawdzono lokalnie. Pełny workflow uruchamiany po tej
zmianie sprawdzi kompilację. W chwili przygotowania poprawki nie powstał nowy

## Co potwierdzono

zakończyła się 30 września o 12:24 UTC. Publiczne API GitHuba potwierdza:

- synchronizacja i integracja źródeł zakończyły się powodzeniem;
- etap kompilacji zakończył się kodem **143** (128 + SIGTERM);
- kontrola obrazu i oba końcowe kroki diagnostyczne zostały pominięte;
- [test samych poprawek źródeł](https://github.com/Luki2421/neo8-orangefox/actions/runs/36709290901) przeszedł.

Kod 143 sam nie dowodzi błędu kompilatora, OOM ani zbyt małego dysku.
Po podłączeniu GitHuba odczytano pełny log: o 12:24:05 UTC runner zgłosił
`The runner has received a shutdown signal`. Ostatnim zakończonym zadaniem
było kopiowanie programu `soong_build` (130/131). Brak komunikatu błędu C++
i potwierdzenia OOM. Przyczyna wyłączenia runnera pozostaje nieustalona.
Poniższa poprawka nie jest potwierdzonym rozwiązaniem tego przerwania.

## Naprawiony błąd konfiguracji

`BoardConfig.mk` ustawia `TW_NO_AUTO_DECRYPT` i
`TW_FORCE_STOCK_THEME_ON_BOOT`, a poprawiony `libfoxui_defaults.go` odczytuje je
z `twrpVarsPlugin`. Brakowało jednak eksportu obu zmiennych przez
`orangefox_soong.mk`. W efekcie GUI nie dostawało tych definicji, choć główny
moduł recovery budowany przez Make otrzymywał własną flagę.

W szczególności właściwa obsługa `neo8preparedecrypt` znajduje się wewnątrz
`#ifdef TW_NO_AUTO_DECRYPT`. Bez tej definicji rzeczywista akcja kończyła się
statusem błędu. Dotychczasowy test C++ sam definiował tę flagę, więc nie wykrywał
usterki konfiguracji.

Poprawka dodaje oba eksporty. Nowy test uruchamia GNU Make na rzeczywistym
`vendor/twrp/config/BoardConfigSoong.mk` i pliku eksportów recovery. Sprawdza
dziewięć kombinacji wartości pustej, `false` i `true`. Test odrzuca oryginalny
plik eksportów i przechodzi po poprawce. Pełny workflow sprawdza to na faktycznie
zsynchronizowanych źródłach przed uruchomieniem kompilatora.

## Pozostałe zmiany

- Pełny build reaguje także na zmiany patchy, wersji źródeł i skryptów integracji.
- Raporty integracji i manifest są wysyłane przed kompilacją. Mogą dzięki temu
  przetrwać późniejsze wyłączenie runnera.
- Podczas kompilacji co 30 sekund zapisywane są RAM, swap, dysk, liczniki cgroup
  i zużycie pamięci procesów. Nagłe wyłączenie nadal może uniemożliwić zapis
  końcowego artefaktu; kopia pomiarów trafia również do bieżącego logu Actions.
- Suma SHA-256 w paczce obrazu wskazuje teraz dostarczony plik
  `OrangeFox-Neo8-development.img`, zamiast niedostępnej ścieżki `out/...`.
- Skrypty hosta używają standardowego katalogu tymczasowego i respektują
  `TMPDIR`; nie wymagają bezwarunkowo `/tmp`. Nie zmienia to ścieżek na telefonie.

## Walidacja lokalna

Przeszły: zastosowanie wszystkich patchy do przypiętych źródeł, kontrola
`git diff --check`, dziewięć przypadków eksportu Soong, sześć testów ramdisku,
testy startu i GUI, ręcznego menu, ochrony operacji KeyMint, zatrzymywania usług,
walidacji właściwości stock, oczekiwania na dotyk oraz zachowania montowań.
Przeszła składnia YAML i Bash wszystkich workflow.

Test kopii SQLite nie został wykonany do końca: lokalnemu środowisku brakuje
`sqlite3.h`. Workflow instaluje `libsqlite3-dev` i nadal wykonuje ten test.
Nie wykonano pełnego linkowania Androida, kontroli nowego obrazu ani testu telefonu.

## Zastosowanie dostarczonego patcha

W katalogu repozytorium, na zgodnej bazie i bez kolidujących lokalnych zmian:

```bash
git apply --check /sciezka/neo8-recovery-fix.patch
git apply /sciezka/neo8-recovery-fix.patch
git add .
git commit -m "Fix Neo8 GUI Soong flags and preserve build diagnostics"
git push
```

Push uruchomi testy i pełny workflow. Można też użyć Actions →
**Neo8 - full Android compilation experiment** → **Run workflow**.
Po powodzeniu kompilacji i kontroli obrazu artefakt nazywa się
`neo8-development-image-unreviewed`. Udana kompilacja nie potwierdza działania
dotyku ani odszyfrowania na RMX8899; obraz pozostaje rozwojowy.


## Kolejna diagnoza i poprawka zasobów — 1 października

[Test źródeł](https://github.com/Luki2421/neo8-orangefox/actions/runs/36732194488)
przeszedł także na GitHubie, łącznie z SQLite. Natomiast
[pełna próba](https://github.com/Luki2421/neo8-orangefox/actions/runs/36732194405)
ponownie zakończyła się SIGTERM podczas generowania grafu Soong. Nowa diagnostyka
pokazała o 15:23:48 UTC 30 września: RSS `soong_build` 14 800 212 KiB,
689 MiB dostępnego RAM i wykorzystane całe 3071 MiB swapu. Na dysku nadal było
około 30 GiB. Sześć sekund później runner został wyłączony. To potwierdza silną
presję pamięci; brak zachowanego komunikatu kernela nie pozwala nazwać tego
potwierdzonym zabiciem procesu przez OOM killer.

Następna próba dodaje swap do łącznej pojemności 15 GiB, zachowując co najmniej
16 GiB wolnego dysku na wynik budowy. Skrypt odmawia zmian na lokalnym komputerze
lub runnerze self-hosted i nie wyłącza istniejącego swapu. Sześć testów hosta
sprawdza wyliczanie rozmiaru, zapas dysku i odmowę działania poza właściwym CI.

Przypięto Soong `6dc77879464584ef3f178cae622134ed0bf19e1e` i dodano poprawkę
jego środowiska uruchomieniowego. Dla `NEO8_LOW_MEMORY_BUILD=1` przekazuje ona
`GOGC=50`, `GOMEMLIMIT=10GiB` i `GOMAXPROCS=2` do `soong_build` poprzez
`PrimaryBuilderInvocation.Env`. Blueprint uruchamia ten proces jako
`env -i $env`, więc zwykłe eksporty w powłoce byłyby tracone.
Limit Go jest miękki; dodatkowy swap daje zapas, jeśli graf wymaga więcej pamięci.
Ustawienia dotyczą narzędzi hosta, nie obrazu recovery ani parametrów telefonu.
Pełna kompilacja po tej zmianie pozostaje do sprawdzenia.
